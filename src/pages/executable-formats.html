Formats de Fichiers Exécutables

Comprendre les formats binaires

Les formats exécutables définissent la structure des fichiers binaires et déterminent comment le système d'exploitation les charge en mémoire pour les exécuter. Les deux formats principaux sont ELF (systèmes UNIX/Linux) et PE (Windows).

Format ELF (Executable and Linkable Format)

Format standard pour les exécutables sous Linux, FreeBSD, et autres systèmes UNIX-like.

Structure d'un fichier ELF

En-tête ELF
Table des en-têtes de programme
.text (code exécutable)
.data (données initialisées)
.bss (données non initialisées)
Autres sections
Table des symboles
Table des en-têtes de section

Composants clés d'un fichier ELF

En-tête ELF

Contient les informations de base sur le fichier :

  • Magic number (0x7F 'ELF')
  • Architecture (32/64-bit)
  • Endianness (little/big)
  • Type de fichier (exécutable, objet, etc.)
  • Machine cible (x86, ARM, etc.)
  • Points d'entrée
Sections importantes
  • .text - Code exécutable
  • .data - Données initialisées
  • .bss - Données non initialisées
  • .rodata - Données en lecture seule
  • .symtab - Table des symboles
  • .dynamic - Informations de liaison dynamique
  • .plt/.got - Tables pour résolution dynamique

Contenu à ajouter : Détails sur le rôle de .plt, .got, .symtab, .dynamic.

.plt (Procedure Linkage Table): Utilisée pour les appels de fonctions externes dans les bibliothèques partagées. Contient du code "trampoline" qui saute vers l'adresse réelle de la fonction (résolue la première fois via le GOT).

.got (Global Offset Table): Table d'adresses utilisées par le code pour accéder aux fonctions et variables globales. Pour les fonctions externes, elle est initialement remplie avec des pointeurs vers le résolveur dynamique, puis mise à jour par le linker dynamique (`ld.so`) avec les vraies adresses lors du premier appel via le PLT.

.symtab (Symbol Table): Contient des informations sur les symboles du fichier (fonctions, variables globales/statiques), utilisés principalement pour le débogage et l'édition de liens statique. Généralement supprimée (`stripped`) des binaires distribués.

.dynamic: Contient des informations nécessaires à l'édition de liens dynamique, comme les bibliothèques requises, l'emplacement du GOT, du PLT, de la table des symboles dynamiques (.dynsym), et de la table des chaînes dynamiques (.dynstr).

Analyse d'un fichier ELF avec les outils

# Afficher l'en-tête ELF
readelf -h executable

# Afficher les sections
readelf -S executable

# Afficher la table des symboles
readelf -s executable

# Afficher les segments
readelf -l executable

# Désassembler la section .text
objdump -d -j .text executable

Format PE (Portable Executable)

Format standard pour les exécutables sous Windows (.exe, .dll, .sys, etc.).

Structure d'un fichier PE

DOS Header & DOS Stub
PE File Header
Optional Header
Section Table
.text (code)
.data (données initialisées)
.rdata (données en lecture seule)
Autres sections

Composants clés d'un fichier PE

En-têtes
  • DOS Header - Commence par "MZ"
  • DOS Stub - Programme DOS affiché si exécuté sous DOS
  • PE Header - Commence par "PE\0\0"
  • Optional Header - Contient des informations sur l'image
  • Section Table - Liste les sections du fichier
Sections courantes
  • .text - Code exécutable
  • .data - Données initialisées
  • .rdata - Données en lecture seule
  • .idata - Table d'importation
  • .edata - Table d'exportation
  • .rsrc - Ressources (icônes, images, etc.)
  • .reloc - Informations de relocalisation

Contenu à ajouter : Détails sur le rôle de .idata, .edata, .rsrc, .reloc.

.idata (Import Data): Contient l'Import Directory Table (IDT) qui liste les DLL externes et les fonctions importées par l'exécutable. Le chargeur Windows utilise cette section pour résoudre les adresses des fonctions importées au moment du chargement.

.edata (Export Data): Contient l'Export Directory Table (EDT) qui liste les fonctions et variables que l'exécutable (souvent une DLL) rend disponibles pour d'autres modules. Permet aux autres programmes d'utiliser les fonctionnalités exportées.

.rsrc (Resource Data): Contient les ressources de l'application, comme les icônes, images, curseurs, boîtes de dialogue, menus, chaînes de caractères (souvent pour la localisation), etc. Organisées en structure arborescente.

.reloc (Relocation Data): Contient les informations de "relocalisation". Si l'exécutable ne peut pas être chargé à son adresse de base préférée (ImageBase), le chargeur doit ajuster (patcher) toutes les adresses absolues dans le code et les données. Cette section indique où ces ajustements sont nécessaires.

Tables d'importation et d'exportation

Les tables d'importation et d'exportation sont cruciales pour l'analyse en reverse engineering car elles révèlent les fonctions utilisées par l'exécutable :

Table d'importation

Liste les fonctions que l'exécutable importe d'autres DLL :

  • Nom des DLL importées
  • Nom ou ordinal des fonctions
  • Adresses des fonctions importées
Table d'exportation

Liste les fonctions que l'exécutable exporte pour d'autres programmes :

  • Nom des fonctions exportées
  • Adresses des fonctions
  • Numéros d'ordinal

Exemples : Modification de Binaires (ELF/PE)

Contenu à ajouter : Exemples simples de modification (patching) d'un binaire pour changer son comportement, par exemple, en modifiant une instruction de saut ou une chaîne de caractères, en utilisant un éditeur hexadécimal ou des outils comme `radare2`.

Patching simple : Modifier une chaîne de caractères

Supposons un programme simple qui affiche "Hello, World!". Cette chaîne est stockée dans une section de données (ex: `.rodata` en ELF, `.rdata` en PE). On peut la localiser avec des outils comme `strings` ou dans un désassembleur, puis utiliser un éditeur hexadécimal (comme HxD, Bless, ou `hexedit`) pour la remplacer par autre chose (par exemple, "Hello, Hack!"), en faisant attention à ne pas dépasser la taille originale ou à gérer les null terminators.

# Exemple avec un éditeur hexadécimal :
1. Trouver l'offset de la chaîne "Hello, World!" dans le fichier binaire.
2. Ouvrir le fichier avec l'éditeur hexadécimal.
3. Naviguer jusqu'à l'offset.
4. Remplacer les octets correspondants à "Hello, World!" (48 65 6C 6C 6F 2C 20 57 6F 72 6C 64 21 00) 
   par ceux de "Hello, Hack! " (48 65 6C 6C 6F 2C 20 48 61 63 6B 21 20 00) - attention à la longueur!
5. Sauvegarder le fichier modifié.
Patching de code : Inverser une condition de saut

Imaginons une vérification de licence simpliste :

if (is_licence_valid()) {\n    printf("Licence OK\n");\n} else {\n    printf("Licence Invalide!\n");\n    exit(1);\n}

En assembleur (x86), cela pourrait se traduire par un appel à `is_licence_valid`, suivi d'un test du résultat (souvent dans `EAX`) et d'un saut conditionnel (par exemple, `jz` - Jump if Zero/Equal, ou `jnz` - Jump if Not Zero/Not Equal) qui saute par-dessus le code "Licence OK" si la licence est invalide.

Avec un désassembleur/débogueur (comme Ghidra, IDA, radare2, x64dbg), on peut localiser cette instruction de saut conditionnel. Pour contourner la vérification, on peut :

  • Remplacer le saut conditionnel par un saut inconditionnel (`jmp`) pour toujours exécuter le code "Licence OK".
  • Remplacer le saut conditionnel par des NOPs (`0x90`) : L'instruction de saut est neutralisée, le flux d'exécution continue vers le code "Licence OK".
  • Inverser la condition du saut : Remplacer un `jz` par un `jnz`, ou vice-versa (il faut trouver l'opcode correspondant).
# Exemple avec radare2 (simplifié):
r2 -w executable  # Ouvrir en mode écriture
aaa               # Analyser le binaire
s sym.main        # Aller à la fonction main (ou là où est la vérification)
pdf               # Afficher le désassemblage pour trouver l'offset du saut (ex: 0x00401050)
"wa jmp 0x00401060" @ 0x00401050  # Remplacer l'instruction à 0x00401050 par un jmp vers le bloc "Licence OK"
# Ou :
"wa nop" @ 0x00401050          # Remplacer l'instruction par un NOP (si elle fait 1 octet, sinon plusieurs wa nop)

Attention: Le patching de binaires peut facilement les corrompre si l'on ne fait pas attention aux tailles d'instructions, aux offsets, et aux effets secondaires. C'est une compétence clé en reverse engineering et en analyse de malware.

Comparaison ELF vs PE

Caractéristique ELF PE
Système d'exploitation Linux, Unix, BSD Windows
Magic number 0x7F 'ELF' 'MZ' + 'PE\0\0'
Extensions courantes Aucune (.so pour lib. partagées) .exe, .dll, .sys
Sections code .text .text
Sections données .data, .bss, .rodata .data, .rdata
Importations .plt, .got .idata
Exportations .dynsym, .dynstr .edata
