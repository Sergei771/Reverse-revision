Fondamentaux du Reverse Engineering

Qu'est-ce que le Reverse Engineering ?

Le reverse engineering (ou rétro-ingénierie) est le processus qui consiste à analyser un système, un dispositif ou un logiciel pour comprendre son fonctionnement interne, sa structure et ses algorithmes sans avoir accès à sa documentation ou à son code source original.

Objectifs et Applications en Cybersécurité

Analyse de Vulnérabilités

Identification des failles de sécurité dans les applications pour les corriger avant qu'elles ne soient exploitées.

Analyse de Malware

Étude des logiciels malveillants pour comprendre leurs mécanismes et développer des contre-mesures.

Contournement de Protections

Analyse des mécanismes de protection pour tester leur efficacité ou les contourner légitimement.

Interopérabilité

Compréhension des formats et protocoles propriétaires pour développer des solutions compatibles.

Ghidra en détail

Ghidra est un outil développé par la NSA et rendu public en 2019. Il offre des fonctionnalités puissantes pour le reverse engineering :

  • Désassembleur multi-plateforme - Supporte de nombreuses architectures (x86, ARM, MIPS, etc.)
  • Décompilateur - Convertit le code machine en pseudo-code C
  • Interface graphique intuitive - Visualisation du graphe des fonctions
  • Scripting - Extensible via Java et Python
  • Collaboration - Permet le travail en équipe sur des projets

Approfondissement : Registres et Pile (x86-32)

Comprendre les registres du CPU et le fonctionnement de la pile est fondamental pour analyser le code assembleur. Voici un aperçu pour l'architecture x86-32 (les noms sont étendus en x86-64, ex: EAX devient RAX).

Détails des Registres principaux
RegistreDescriptionUsage courant
EAXAccumulateurStocke les résultats d'opérations, valeur de retour des fonctions
EBXBasePointeur de base pour accès mémoire (souvent sauvegardé)
ECXCompteurUtilisé comme compteur dans les boucles (ex: `LOOP`)
EDXDonnéesExtension de EAX pour certaines opérations (multiplication, division), I/O
ESISource IndexPointeur source pour opérations sur chaînes/mémoire
EDIDestination IndexPointeur destination pour opérations sur chaînes/mémoire
ESPStack PointerPointe vers le sommet actuel de la pile (change avec PUSH/POP)
EBPBase PointerPointe vers la base du "stack frame" de la fonction courante (utilisé pour accéder aux arguments et variables locales)
EIPInstruction PointerContient l'adresse de la prochaine instruction à exécuter (ne peut être modifié directement)
EFLAGSFlags RegisterContient des bits indiquant le résultat de la dernière opération (Zero Flag ZF, Carry Flag CF, Sign Flag SF, Overflow Flag OF, etc.)
Fonctionnement de la Pile (Stack) :

La pile est une zone mémoire LIFO (Last-In, First-Out) utilisée pour stocker temporairement des données, passer des arguments aux fonctions, stocker les variables locales, et sauvegarder l'état lors des appels de fonction.

  • Croissance : Sur x86, la pile croît vers les adresses basses (les nouvelles données sont à des adresses plus petites).
  • ESP : Pointe toujours vers le sommet actuel de la pile (la dernière donnée empilée).
  • PUSH src : Décrémente ESP puis copie `src` à l'adresse pointée par ESP.
  • POP dest : Copie la valeur à l'adresse d'ESP dans `dest` puis incrémente ESP.
Détails : Appel de Fonction et Stack Frame

Lorsqu'une fonction est appelée (`CALL` instruction) :

  1. Les arguments sont souvent poussés sur la pile (généralement de droite à gauche en convention cdecl).
  2. L'instruction `CALL` pousse l'adresse de retour (l'instruction après le `CALL`) sur la pile.
  3. Le contrôle saute à l'adresse de la fonction appelée.
  4. Prologue de la fonction appelée :
    • Sauvegarde l'ancien EBP : `PUSH EBP`
    • Établit le nouveau frame : `MOV EBP, ESP`
    • Alloue de l'espace pour les variables locales : `SUB ESP, taille_locales`
  5. Le corps de la fonction s'exécute (accès aux arguments via `[EBP + offset_positif]`, aux locales via `[EBP - offset_négatif]`).
  6. Épilogue de la fonction appelée :
    • Libère l'espace des locales : `MOV ESP, EBP` (ou `LEAVE`)
    • Restaure l'ancien EBP : `POP EBP` (inclus dans `LEAVE`)
  7. L'instruction `RET` dépile l'adresse de retour dans EIP, le contrôle revient à l'appelant.
  8. L'appelant nettoie les arguments de la pile (si nécessaire selon la convention d'appel).

Comprendre ce mécanisme est crucial pour suivre le flux d'exécution et analyser les variables locales et les paramètres.

Ghidra en Pratique : Exemple Simple

Voyons un exemple très simple d'utilisation de Ghidra avec un programme "Hello World" en C compilé.

// hello.c
#include <stdio.h>

void greet(const char* name) {
    printf("Hello, %s!\n", name);
}

int main() {
    char myName[] = "Reverse Engineer";
    greet(myName);
    return 0;
}

// Compilation (exemple Linux 32 bits):
// gcc -m32 -no-pie -fno-stack-protector -o hello hello.c
Étapes détaillées dans Ghidra
  1. Créer un projet : File -> New Project... -> Non-Shared Project -> Choisissez un répertoire et un nom de projet.
  2. Importer le fichier : File -> Import File... -> Sélectionnez votre binaire `hello` compilé. Cliquez sur OK dans la fenêtre d'importation (le format ELF/PE devrait être détecté). Double-cliquez sur le fichier dans le projet pour l'ouvrir dans le CodeBrowser.
  3. Analyser : Ghidra vous demandera d'analyser le fichier. Cliquez sur "Yes". Acceptez les options par défaut dans la fenêtre "Analysis Options" (ou ajustez si nécessaire) et cliquez sur "Analyze".
  4. Trouver `main` : Dans la fenêtre "Symbol Tree" (Window -> Symbol Tree si non visible), dépliez "Functions" et cherchez `main`. Double-cliquez dessus.
  5. Explorer :
    • La fenêtre "Listing" montre le code désassemblé. Vous devriez voir l'appel (`CALL`) à la fonction `greet`.
    • La fenêtre "Decompiler" (Window -> Decompiler) montre une tentative de reconstruction en pseudo-code C. Vous devriez y reconnaître la logique de `main` et l'appel à `greet`.
  6. Renommer : Dans le décompilateur, cliquez sur une variable locale (ex: `local_...` représentant `myName`). Appuyez sur `L` (ou clic droit -> Rename Variable) et donnez-lui un nom plus significatif, comme `studentName`. Le changement se répercute. Faites de même pour la fonction `greet` si elle a un nom générique (`FUN_...`): cliquez sur son nom dans le décompilateur ou le listing, appuyez sur `N` (ou clic droit -> Rename Function).
  7. Commenter : Cliquez sur une ligne dans le désassembleur ou le décompilateur. Appuyez sur `;` (point-virgule) pour ajouter un commentaire expliquant cette ligne.

Cet exemple simple illustre le workflow de base : importer, analyser, naviguer, comprendre via le désassemblage et la décompilation, et annoter pour améliorer la clarté.

Procédure d'Analyse d'un Binaire Simple

Analyser un binaire inconnu demande une approche méthodique. Voici les étapes clés pour un petit programme C compilé :

Voir les étapes détaillées
  1. Reconnaissance initiale (Statique) :
    • Utiliser `file mon_binaire` pour identifier le type de fichier (ELF 32/64-bit, PE, etc.).
    • Exécuter `strings mon_binaire` pour extraire les chaînes de caractères lisibles (messages d'erreur, noms de fichiers, URLs, constantes...). Cela peut donner des indices rapides sur la fonctionnalité.
    • Examiner les imports (fonctions de bibliothèques externes utilisées) et les exports (fonctions fournies par le binaire). Sous Linux: `readelf -s mon_binaire | grep FUNC`, `objdump -T mon_binaire`. Sous Windows: outils comme PE-bear, CFF Explorer, ou Ghidra/IDA. Les imports révèlent les capacités (ex: `printf` -> affichage, `socket` -> réseau, `CreateFile` -> manipulation de fichiers).
  2. Analyse Statique Approfondie (ex: Ghidra/IDA) :
    • Charger le binaire dans l'outil et lancer l'analyse automatique.
    • Identifier le point d'entrée principal (souvent `main`, `start`, ou une fonction similaire).
    • Analyser le code désassemblé et/ou décompilé de la fonction principale. Suivre le flux logique principal.
    • Identifier les appels à d'autres fonctions (internes ou externes via les imports). Analyser ces fonctions appelées.
    • Repérer les structures de contrôle : boucles (`for`, `while`), conditions (`if`, `switch`). Le graphe de fonction est très utile ici.
    • Rechercher les accès mémoire importants (variables globales, structures, arguments).
    • Renommer les variables, fonctions, et ajouter des commentaires au fur et à mesure de la compréhension. C'est crucial pour ne pas se perdre.
  3. Analyse Dynamique (si besoin, ex: GDB/x64dbg) :
    • Utiliser un débogueur si l'analyse statique n'est pas suffisante pour comprendre un comportement ou une valeur spécifique.
    • Placer des points d'arrêt (`breakpoint`) aux endroits clés (début de `main`, avant/après un appel de fonction suspect, début d'une boucle).
    • Exécuter le programme (`run`) et l'inspecter lorsqu'il s'arrête.
    • Examiner l'état des registres (`info registers`) et de la mémoire (`x/`).
    • Avancer pas à pas (`stepi` pour une instruction assembleur, `nexti` pour passer par-dessus un appel) pour observer les changements d'état.
    • Fournir différentes entrées au programme pour voir comment il réagit.
  4. Synthèse et Documentation :
    • Résumer le fonctionnement global du programme.
    • Documenter les algorithmes clés, les structures de données importantes, et les éventuelles vulnérabilités trouvées.
    • Le but est de reconstruire une compréhension fonctionnelle du binaire.
